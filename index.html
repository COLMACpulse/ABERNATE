GOVERN  |  CONTROL  |  PROTECT

An agent gets approved once. Then it acts a thousand times.

ABERNATE checks each action before it happens. Four rules have to agree, or the action does not run. A person has to clear a release, and that person can only say no. Every step writes a signed receipt, and a recipient who was given the right verification key can check it themselves.

Approval happens once. The work happens all day.

Security review does real work. It decides which AI tools are allowed, which vendors clear procurement, and what data those tools can see. All of that is about what the agent is.

The gap that follows is not our observation. Four independent groups have described the same missing layer in 2026 alone, under four different names, and at least one has argued the whole category is aimed at the wrong place. Sources in the technical packet.

Then the agent runs. It calls an API, writes to a database, triggers a workflow, holds a document. Nothing sits between that call and the consequence, and more than half of agents in production run with no oversight or logging at all. A third of organisations say they could not immediately stop a rogue agent.

A reviewer has two options: hold the project, or let it through with the agent restricted. More than 80% of organizations report doing the second at least sometimes, and end up running a smaller version of what they paid for.

ABERNATE covers the part nobody checks: what the agent is allowed to do, at the moment it does it.

Agents ship late, or ship restricted.

An agent that clears review with its autonomy cut is not a win, it is the budget spent and the capability withheld. An agent still in review at month six is the same money with nothing to show at all.

Both happen for one reason: the reviewer has no control to point at, so the only levers left are delay and restrict. Give them a gate that refuses on the action itself, and a signed record of every refusal and every clearance, and the conversation changes from how much to take away to what evidence gets produced.

The four checks

Permission is not one setting. Before an action runs, four separate questions have to answer yes.

01Can this worker do this at all? Its contract lists the actions it has and the paths it may read.
02Does the command being run permit it? A command is a narrower grant than the worker's full capability.
03Does standing policy allow it? Risk class, network access, evidence thresholds, step limits.
04Did this job actually ask for it? An action nobody requested is refused even when all three above allow it.
ALL FOUR, OR NOTHING  ·  five strong properties and one dead one is a refusal, and the dead one gets named. Nothing averages out.

A named human has the last word and can only say no. Their GO cannot push an action through a check that already failed, and a policy written without that gate is rejected the moment it loads, so no engineer disables it by forgetting it.

Every step writes a receipt, hash-linked to the one before it and signed. A step can cover many files, so this is a record per step, not per file touched. That file goes to the customer's lawyer, the SOC 2 auditor or opposing counsel. Each checks it with a command that ships in the package, against a verification key they were given separately. They still have to trust where that key and that package came from. What they do not have to accept is the operator's word that the ledger is unaltered.

What makes it different

  • One bad check stops the action Scoring systems let a strong result cover a bad one. Here a single failed condition stops the action and the output names which one. There is no total high enough to pass a refusal.
  • The attacks that beat it are in the box Ten forgeries were run against its evidence chain and all ten are caught. One of them was disclosed for months as structurally unfixable, and is now closed. Each is a passing test, so none can be quietly dropped. They are ten attacks this team thought of; an attack nobody here thought of is not in that number. The list, the method, and the record of which ones got through first, ship with the packet.
  • Every claim here has been attacked, including by us Some of the strongest tests in here exist because earlier versions failed them. Those failures remain in the record: the human gate was wrong once, tail truncation survived once, a full-chain reforge exposed a structural weakness, and closing it with signatures opened a new attack that key pinning then closed. Each is now a passing test, so none can be quietly dropped.

The check ships in the package. reproduce.py downloads that tarball, verifies the sha256, grants the corpus through a contract it prints and then revokes, runs the sweep, and compares the five figures above against what it measured. Exit 0 means those five held on that machine. It takes about nine seconds.

One more thing happened on the way in, and it was not staged. The first attempt was refused before a single file was read: read path outside authority. No worker contract declared that corpus, so nothing touched it until one did. That is the gate working on data it had never seen.

What it will not do

  • It cannot stop whoever holds the signing key Receipts are signed, so the customer, the auditor and opposing counsel cannot forge one. The security team holding the signing key still can. That is what a signature means, and it turns "could this have been faked" into "who held the key on 14 March", which access records already answer.
  • It does not prove the decision was right It records which authority permitted the action, under what capability, and who cleared it. That record is checkable. Whether the action was the right one is not in it. Whether holding that document was legally correct is a judgement a lawyer makes, and no machine on this page makes it. Anyone who tells a court otherwise will be taken apart on it.
  • It has been run on thousands of files, not millions The published run covers 4,579 files and 100 MB of one public source release. Throughput at enterprise document volume has not been measured, and no claim is made about it. The corpus is code, not email or PDFs, so the file handling is proven and the document-type coverage is not.
  • It checks the action, not the thinking behind it There is a documented argument that this is the wrong layer: that governance has crowded onto execution risk while the real blind spot sits upstream, in how a model framed the options before any action was proposed. That critique is correct about the limit. ABERNATE rules on what an agent is permitted to do. It has nothing to say about why the agent wanted to do it, and a related objection holds that intercepting after reasoning completes is weaker than governing the reasoning itself. Both are worth reading before buying.
  • It does not replace whatever builds the agents It sits underneath whatever framework the agents are built with, and rules on the actions they take.

What it needs to run

46 of 46 tests pass from a cold extraction on Python 3.12. Standard library only. No dependencies, no network, no account, no GPU, nothing to host. The internal file manifest is generated from the folder and refuses when the two disagree, because a hand-typed count is what went wrong twice.
